# 调查管理与知识核验的实施拆解及工作量评估

日期：2026年11月11日

## 一、实施判断

现有工程适合增量改造。采集执行、原文归档、字段契约、结构化结果预览、参数化 SQL 写入及图谱已经形成基础；本轮主要补齐统一读取、核验结果、知识可用状态和调查恢复。采用现有后端内的模块组织，复用数据库和网页入口。

最小可用闭环预计需要 16—24 个有效工程小时，即一人约 2—3 个工作日；完成本轮六项建设并联调，预计 38—62 个有效工程小时，即约 5—8 个工作日。最小闭环包含在完整工作量内，不另行相加。估计按熟悉现有项目的一名开发者、每天约八小时有效工作计算，包括小样本回归与修复，不是模型执行时长或日历完成承诺。

估计范围是现有企业、产品和技术类型的首批核验规则与流程。全部历史资料重新抽取、所有字段的证据策略补齐、开放域语义自动判定、复杂研判以及报告自动重写，需要在后续范围中单独评估。第一版允许无法确定的记录进入待查。

## 二、现有代码提供的接入点

以下路径以 `research-workbench/` 为起点。

| 接入点 | 当前职责 | 本轮改造 |
| --- | --- | --- |
| `web/api/topic_store.py` | 专题、调查运行、任务及旧知识快照 | 统一业务知识读取，保留已有运行记录，分离采集和加工状态 |
| `web/api/topic_research.py` | 本地查询、任务计划、采集、停止与恢复 | 使用统一快照，接收具体补查任务，改进恢复及结束原因 |
| `web/api/research_database.py` | 新研究库查询与来源读取 | 提供按核验状态和有效范围过滤的业务读取接口 |
| `web/api/knowledge_handoff/contracts.py` | 字段契约、归一与结果校验 | 增加条件、事实性质和规则版本的标准输入 |
| `web/api/knowledge_handoff/service.py` | 原文、结果预览、提交和独立摘要 | 在现有 preview/commit 路径接入核验，继续分开保存正文与摘要 |
| `web/api/knowledge_handoff/review.py` | 影子数据库预览、实体选择、冲突提示、版本检查和 SQL 提交 | 把可发布部分和待查部分分开，增加核验版本检查 |
| `searchos/knowledge_store/schema.sql` 与 `database.py` | 七维数据库、来源、断言、核验决定和历史 | 通过迁移补充核验元数据及视图，保留现有断言历史和约束 |
| `searchos/agents/runtime.py` | Agent 构建与默认内存检查点 | 选定恢复边界后接持久化检查点，与业务运行标识对应 |
| `searchos/collection_policy/` | 现有采集排序及反馈 | 接收任务级核验需求，不把全部空字段变成搜索目标 |
| `web/frontend/src/components/topics/` 等现有组件 | 原文、知识库、图谱和导入展示 | 增加核验原因、争议与历史信息，沿用现有图谱 |

旧专题快照仍从旧知识库构造，而已接入的本地字段查询使用新研究库。这是第一项需要解决的数据一致性问题。

现有导入预览会复制数据库并计算整体指纹，提交时拒绝使用已经过期的预览。第一版保留这套保护并采用串行发布队列；高并发下细化读取集合和版本检查，放在后续性能工作中。

## 三、建议新增的模块与接口

建议在 `searchos/knowledge_quality/` 增加独立的纯处理模块，网页 API 负责调用与持久化，模块本身不启动采集或付费模型。

| 模块 | 输入与输出 |
| --- | --- |
| `models.py` | 定义候选记录、已对齐记录、核验项目、差异、处理决定与补查请求 |
| `registry.py` | 加载固定版本的字段定义、比较规则、证据要求与推理规则 |
| `alignment.py` | 输入候选名称和上下文，输出实体及属性映射、匹配依据或待查项 |
| `normalization.py` | 保留原值，输出标准单位、数值区间、时间角色和条件表示 |
| `comparison.py` | 比较抽取与原文、新旧记录、结论与前提，输出等价、条件分离、演化或差异 |
| `evidence.py` | 根据来源路径、原文和适用范围生成核验结果，保留来源独立性未明状态 |
| `decision.py` | 根据通过、失败、未明项目输出修订、撤回、补查、争议或维持 |

接口围绕四种结果组织：

- `CandidateBundle`：来源版本、本体版本、对象、字段或关系、原值、条件、时间、事实性质、证据位置。
- `VerificationResult`：已对齐记录、核验项目、差异、来源组依据及处理决定。
- `FollowupRequest`：具体缺口、关联断言、所需材料、已检查来源和任务范围。
- `PublishReceipt`：发布记录、待查记录、版本、引用变动及可重试事项。

名称为设计提案。实现时复用现有模型中的等价字段，避免维护两份相同事实。

数据库增量围绕本体发布版本、核验运行、核验项目、来源传播关系及冲突案件组织。现有 `claims`、`claim_evidence`、`review_decisions`、`claim_history` 和 `maintenance_tasks` 继续承担事实、引用、修订及任务管理。核验状态与既有入库状态分开，旧 accepted 记录不批量自动变为按新规则核验通过。

## 四、六项实施工作与估计

| 顺序 | 工作 | 验收结果 | 难度 | 有效工程时间 |
| --- | --- | --- | --- | --- |
| 1 | 统一专题读取与第一版契约 | 本地查询、专题快照、图谱和加工过程指向同一业务实体与来源；旧数据仍可查看 | 中 | 4—6 小时 |
| 2 | 对象、字段、条件及来源对齐 | 别名可定位，版本和条件不混合；来源链可追溯，同源转载不重复计数 | 中高 | 8—12 小时 |
| 3 | 首批核验规则与处理器 | 三种比较和四级内容路由可执行；每项有规则、证据和通过/失败/未明结果 | 高 | 8—14 小时 |
| 4 | 版本化入库与修订状态 | 可用和待查分开；重复提交不重复入库；已证错误停用；过期预览拒绝发布 | 中高 | 6—10 小时 |
| 5 | 调查状态与补查衔接 | 采集与加工分别结束；补查有具体问题；中断后恢复已有运行，受预算和联网设置约束 | 中 | 6—10 小时 |
| 6 | 网页接入及小样本联调 | 可看任务进度、原文、核验原因、争议和修订历史；图谱现有交互正常 | 中 | 6—10 小时 |
| 合计 | 本轮完整实现 | 一条材料能够完整进入并维护知识库 | 中高 | 38—62 小时 |

最小闭环优先做第1项与第2—4项的纵向子集：选少量已有记录，按第一版规则完成对齐、核验、预览提交和历史查询，复用现有网页导入入口。预计 16—24 小时。第5—6项完善调查反馈与日常可用性。

## 五、主要难点与控制办法

### 语义检查的准确率取决于条件和证据定位

字符串命中不能证明对象、否定和事件状态理解正确。第一版先支持已有结构化条件和明确原文位置，复杂表达作为未明项保存；模型辅助核验接口独立配置，不因提交资料自动开启付费抽取。

### 来源独立性不能仅凭网站或相似度推定

文本相似用于找候选，引用链和形成记录用于确认来源组。找不到原始记录时保留待查原因，页面数量不当作独立证据数量。证据需求按事实类型配置，声明与实测分别处理。

### 历史数据与新规则需要兼容

新规则从明确版本开始生效。旧数据保留现有来源及状态，单独显示尚未按本版核验；按调查范围和实际使用逐批补验。字段定义以单一目录为权威来源，LinkML 导入导出通过一致性检查后再作为生成入口。

### 修订与恢复必须避免重复发布

继续利用签名写入计划、来源版本检查和提交回执，补充核验版本与处理标识。第一版串行发布，减少整库指纹与并发写入之间的冲突。调查恢复先查询已有采集任务和提交回执，再决定接续或重试。

## 六、开源复用安排

LangGraph、NetworkX、Pydantic 已在现有项目依赖中。第一批优先复用已有调用位置，新增 RapidFuzz 和 Pint 用于候选匹配及单位转换。LinkML 负责定义及契约生成适配，领域规则继续由本项目实现。

第一版不要求新建图数据库，也不要求部署完整 OpenCTI。RDF/SHACL 可在图约束需求明确后接入；本轮的结构、值域、条件与证据检查优先以现有数据库约束和规则函数实现。

代码复用清单：

- [RapidFuzz](https://github.com/rapidfuzz/RapidFuzz)

## 七、验证范围与交付

首先使用临时测试数据库和少量现有材料进行离线验证，覆盖同源转载、单位等价、条件不同、错列、计划误写完成、概括超范围、直接来源矛盾、撤回无更正、并发版本变化和中断恢复。采用小样本验收，不启动全量实验或全库抽取。

每个阶段交付代码、数据库迁移、针对性检查及可查看的运行结果。正式数据写入前保留本地备份；测试数据库与业务库分别配置。现有实验目录继续独立，不将实验采集资料、分数或运行状态导入业务前后端。

本次工作完成了方案文档、私有仓库代码备份及实现评估，以上功能改造尚未开始。
